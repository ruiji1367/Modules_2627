WHY THIS MATTERS

Requirements never stay still

A payroll system that only ever computes salary in one way, for one country, forever — doesn't exist. New payment methods, new tax rules, new report formats: change is the normal condition of software, not the exception.

  • Rigidity — one small change forces you to edit code in many unrelated places.
  • Fragility — fixing one thing breaks something else that seemed unrelated.
  • Immobility — you can't reuse a piece of the system elsewhere because it's tangled with everything around it.
SOLID is not a checklist to memorize — it's a set of answers to one recurring question:

"What happens to this code the next time a requirement changes?"

Ask that question on every slide that follows.
THE PAYOFF

Good design makes change cheap

Each SOLID principle targets one specific way a class can become rigid, fragile, or immovable. We'll meet each one through a small, realistic C# scenario: broken code first, then the fix, then why the fix actually holds up.

SRP — one reason to change OCP — extend without editing LSP — substitutes must behave ISP — don't force unused methods DIP — depend on abstractions
SCENARIO — PAYROLL SYSTEM

One "Employee" class, three jobs

A junior dev adds every payroll-related method straight onto Employee. It compiles. It works today.

Employee.cs — BEFORE
public class Employee
{
    public string Name;
    public double HoursWorked;

    public double CalculatePay()
    {
        return HoursWorked * 250; // rate/hr
    }

    public string ReportHours()
    {
        return $"{Name} worked {HoursWorked}h";
    }

    public void SaveToDatabase()
    {
        // opens a connection, inserts a row
        Console.WriteLine("Saving employee...");
    }
}

What could go wrong?

  • Finance changes the pay formula → you edit Employee.
  • HR changes the report layout → you edit Employee again.
  • The DBA changes the schema → you edit Employee a third time.
  • Three unrelated teams now share one fragile file.
QUICK CHECK
Employee.CalculatePay(), ReportHours(), and SaveToDatabase() live in one class. Which principle is violated — and why?
SRP — Single Responsibility. Payroll math, reporting, and persistence are three separate reasons for this class to change. When one class answers to three different "bosses" (Finance, HR, the DBA), a change requested by any one of them risks breaking the others.
THE FIX

Split by responsibility, not by convenience

Employee.cs — AFTER
public class Employee
{
    public string Name;
    public double HoursWorked;
}

public class PayCalculator
{
    public double CalculatePay(Employee e)
        => e.HoursWorked * 250;
}

public class HoursReporter
{
    public string Report(Employee e)
        => $"{e.Name} worked {e.HoursWorked}h";
}

public class EmployeeRepository
{
    public void Save(Employee e)
    {
        Console.WriteLine("Saving employee...");
    }
}

Why this holds up

  • Finance can rewrite PayCalculator without touching HR's code.
  • Employee becomes a plain, stable data holder.
  • Each class now has exactly one reason to change.
  • Any class can be unit-tested — and reused — on its own.
SCENARIO — PAYMENT SYSTEM

A method that grows forever

Every new payment method means opening this method again and adding another branch.

PaymentProcessor.cs — BEFORE
public class PaymentProcessor
{
    public void Pay(string type, double amount)
    {
        if (type == "CreditCard")
        {
            Console.WriteLine(
                $"Charging card: {amount:C}");
        }
        else if (type == "PayPal")
        {
            Console.WriteLine(
                $"Charging PayPal: {amount:C}");
        }
        // GCash? Maya? another if-branch...
    }
}

What could go wrong?

  • Adding GCash means editing tested, working code.
  • A typo in an unrelated branch can break Credit Card payments.
  • Every new payment type raises the risk of regressions.
  • The class is never really "done" — it's always being reopened.
QUICK CHECK
Adding a new payment method requires editing PaymentProcessor's existing if/else chain. Which principle is at stake?
OCP — Open/Closed Principle. A class should be open for extension (you can add new behavior) but closed for modification (you don't have to edit its existing, already-tested code to do it). Here, every new payment type forces a modification.
THE FIX

Extend through an interface, not an if-chain

PaymentProcessor.cs — AFTER
public interface IPaymentMethod
{
    void Pay(double amount);
}

public class CreditCardPayment : IPaymentMethod
{
    public void Pay(double amount) =>
        Console.WriteLine($"Charging card: {amount:C}");
}

public class GCashPayment : IPaymentMethod
{
    public void Pay(double amount) =>
        Console.WriteLine($"Charging GCash: {amount:C}");
}

public class PaymentProcessor
{
    public void Process(IPaymentMethod method, double amount)
        => method.Pay(amount);
}
// PayMayaPayment can be added later with
// zero changes to PaymentProcessor

Why this holds up

  • PaymentProcessor never changes again for a new payment type.
  • New behavior = a new class implementing IPaymentMethod.
  • Existing, tested payment types stay completely untouched.
  • Risk of regression drops because nothing old is being edited.
SCENARIO — LICENSE SYSTEM

Can every subclass stand in for its parent?

License.cs — VALID SUBSTITUTION
public abstract class License
{
    public abstract bool IsValid();
}

public class PaidLicense : License
{
    public override bool IsValid() => true;
}

public class TrialLicense : License
{
    private DateTime expiresOn;
    public TrialLicense(DateTime exp)
        => expiresOn = exp;

    public override bool IsValid()
        => DateTime.Now < expiresOn;
}
// Any List<License> can call IsValid()
// safely, regardless of which one it holds.
License.cs — VIOLATION
public class LifetimeLicense : License
{
    public override bool IsValid()
    {
        throw new NotSupportedException(
            "Must be checked manually");
    }
}
// Code that trusted every License to just
// return true/false now crashes when it
// happens to receive a LifetimeLicense.
QUICK CHECK
LifetimeLicense throws an exception instead of returning true/false like every other License. Which principle does it break?
LSP — Liskov Substitution Principle. Anywhere the code expects a License, it must be safe to hand it any subclass without surprises. Throwing where callers expect a boolean breaks that promise — the subtype has changed the contract, not just the implementation.
WHY IT MATTERS

Substitutability is a promise, not a suggestion

Inheritance says "a TrialLicense IS-A License." LSP asks a harder question: can code written against License use a TrialLicense — or a LifetimeLicense — without checking which one it got?

  • If a subclass narrows what's accepted or widens what can go wrong, callers can no longer trust the parent type.
  • The fix isn't always "add a check" — it's often a sign LifetimeLicense doesn't truly belong in this hierarchy, or needs its own explicit handling path.
  • LSP violations are usually discovered as runtime crashes, which makes them expensive to catch late.
SCENARIO — ONLINE PAYMENT VS. CASH ON DELIVERY

A "fat" interface forces unused methods

IPaymentMethod.cs — BEFORE
public interface IPaymentMethod
{
    void Pay(double amount);
    void Refund(double amount);
    void SaveCardDetails(string cardNumber);
}

public class CashOnDelivery : IPaymentMethod
{
    public void Pay(double amount) =>
        Console.WriteLine("Pay on delivery");

    public void Refund(double amount) =>
        Console.WriteLine("Refund in cash");

    public void SaveCardDetails(string cardNumber)
    {
        throw new NotImplementedException();
        // COD has no card to save!
    }
}

What could go wrong?

  • CashOnDelivery is forced to implement a method it has no use for.
  • That method exists only to satisfy the compiler — it throws at runtime instead.
  • Anyone calling SaveCardDetails on a COD order finds out the hard way.
QUICK CHECK
CashOnDelivery must implement SaveCardDetails() even though it never uses it. Which principle is violated?
ISP — Interface Segregation Principle. A class shouldn't be forced to implement methods that are irrelevant to it. One bloated interface should become several small, focused ones, so each class only implements what it actually needs.
THE FIX

Split one fat interface into several small ones

Payments.cs — AFTER
public interface IPayable
{
    void Pay(double amount);
}
public interface IRefundable
{
    void Refund(double amount);
}
public interface ICardStorable
{
    void SaveCardDetails(string cardNumber);
}

public class CashOnDelivery
    : IPayable, IRefundable
{
    public void Pay(double amount) =>
        Console.WriteLine("Pay on delivery");
    public void Refund(double amount) =>
        Console.WriteLine("Refund in cash");
}

public class CreditCardPayment
    : IPayable, IRefundable, ICardStorable
{
    public void Pay(double amount) => ...;
    public void Refund(double amount) => ...;
    public void SaveCardDetails(string c) => ...;
}

Why this holds up

  • CashOnDelivery only implements what it can actually do.
  • No more NotImplementedException landmines at runtime.
  • Each interface describes one capability — easy to combine, easy to reason about.
SCENARIO — NOTIFICATION SYSTEM

Locked into one concrete class

UserManager.cs — BEFORE
public class EmailNotifier
{
    public void Send(string message) =>
        Console.WriteLine($"Email: {message}");
}

public class UserManager
{
    private EmailNotifier notifier
        = new EmailNotifier();

    public void Register(string user)
    {
        // ...registration logic...
        notifier.Send($"Welcome, {user}!");
    }
}
// UserManager is welded to EmailNotifier.
// Want SMS instead? Edit UserManager.

What could go wrong?

  • UserManager — high-level logic — depends directly on EmailNotifier, a low-level detail.
  • Switching to SMS, or supporting both, means editing UserManager itself.
  • You can't unit-test UserManager without actually sending an email.
UserManager creates and calls EmailNotifier directly, with no abstraction in between. Which principle is violated?
QUICK CHECK
DIP — Dependency Inversion Principle. High-level modules (business logic like registration) shouldn't depend directly on low-level modules (delivery mechanisms like email). Both should depend on an abstraction — an interface — instead.
THE FIX

Depend on an interface, inject the detail

UserManager.cs — AFTER
public interface INotifier
{
    void Send(string message);
}

public class EmailNotifier : INotifier
{
    public void Send(string message) =>
        Console.WriteLine($"Email: {message}");
}

public class SmsNotifier : INotifier
{
    public void Send(string message) =>
        Console.WriteLine($"SMS: {message}");
}

public class UserManager
{
    private readonly INotifier notifier;

    public UserManager(INotifier notifier)
    {
        this.notifier = notifier; // injected
    }

    public void Register(string user)
        => notifier.Send($"Welcome, {user}!");
}

Why this holds up

  • UserManager → INotifier ← EmailNotifier / SmsNotifier: both sides depend on the interface.
  • Swapping notification channels needs zero edits to UserManager.
  • Tests can inject a fake INotifier — no real email or SMS required.

OrderService — spot every violation

OrderService.cs
public class OrderService
{
    public void PlaceOrder(Order order, string payType)
    {
        if (order.Items.Count == 0)
            throw new Exception("Empty order");

        double total = 0;
        foreach (var item in order.Items)
            total += item.Price;

        if (payType == "CreditCard")
            ChargeCard(total);
        else if (payType == "GCash")
            ChargeGCash(total);
        // new payment type? edit this again

        SqlConnection conn =
            new SqlConnection("...");
        conn.Open();
        // ...insert order directly...

        SmtpClient smtp = new SmtpClient();
        smtp.Send("Order confirmed!");
    }

    private void ChargeCard(double a) { }
    private void ChargeGCash(double a) { }
}

WHY EACH ONE APPLIES

OrderService, explained

  • SRP — validation, total calculation, payment, database access, and email are five separate responsibilities crammed into one method.
  • OCP — the if/else on payType must be edited every time a new payment method is added.
  • DIP — OrderService creates SqlConnection and SmtpClient directly, instead of depending on abstractions it could swap out or mock in tests.

Notice that fixing all three usually means the same move: pull each concern into its own class behind an interface — exactly the pattern from SRP, OCP, and DIP earlier in this deck.

RECAP

Five questions to ask about any class

  • SRP — Does this class answer to more than one "boss"?
  • OCP — Can I add new behavior without editing existing, tested code?
  • LSP — Can every subclass replace its parent without surprises?
  • ISP — Is any class forced to implement a method it never uses?
  • DIP — Does high-level logic depend on a concrete detail, or an abstraction?

None of this is about following rules for their own sake — it's about keeping change cheap.
